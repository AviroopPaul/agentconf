The problem

The config is there. Nobody knows it exists.

Every coding agent keeps its knobs in a dotfolder. The vendors document hundreds of them: sandbox rules, effort levels, hooks, memory budgets, permission modes, MCP gating, statusline commands, plugin marketplaces. Almost none of it is discoverable from inside the agent. So people run on defaults, copy a settings.json from a blog post, and never look again.

What you get

Every setting, explained, with the docs one click away.

The UI knows nothing about individual keys. Everything it says comes from a schema pack: type, default, scope, a one-line summary, a longer note when the summary is not enough, and a deep link to the vendor's own page. New vendor setting on Tuesday, new pack on Tuesday.

Explore

Default view: what you have not touched

538 keys across four agents, grouped by category or by cross-agent concept, filtered to unset by default. Search hits key names, summaries and concepts. Enterprise-only keys are hidden until you ask.

  • Set vs. unset, per agent, at a glance
  • Experimental, deprecated and removed flags called out
  • Your current value, masked if it looks like a secret
Agent

One page per agent, everything it reads

Settings by category, then every file and directory the agent looks at, whether or not it exists yet. State directories show size only. Credential files are marked and never opened.

  • Expand a key for the long note, allowed values, source file
  • Skills, MCP, hooks, plugins, rules, trusted projects
  • Instruction files, with AGENTS.md interop flagged
Skills

Which agent can see which skill

SKILL.md became a cross-vendor convention, and most people share one tree with symlinks. This matrix resolves every link to its real path and shows coverage per agent. Half-shared skills light up.

  • Symlink, local copy, missing, broken
  • Vendor-managed skills kept separate
  • Filter to everywhere, partial, or one agent
MCP

One server list, four storage formats

MCP is the one tools contract every agent shares, and every agent stores it differently. agentconf reads all of them and groups by name, so you can see which agents can reach a server and whether the definitions agree.

  • stdio and HTTP transports, user and project scope
  • Env and header values never read, only their names
  • Drift between agents flagged
Doctor

Diagnostics an editor cannot give you

Cross-agent drift, broken symlinks, deprecated keys still set, skills missing from some agents, keys the pack does not know, binaries that fail to run, state directories past a gigabyte. Every finding says what would resolve it. Nothing is changed for you.

  • Errors, warnings, notes, filterable by check
  • Also available as agentconf doctor in the terminal
  • Exit code 1 on errors, so it fits in a dotfiles CI
Usage

What each agent has accumulated

Sessions, prompts, messages, projects, disk. Claude Code's own stats cache gives per-model tokens, activity by day, and the hours you actually work. Counts and timestamps only. Prompt text is never read.

  • 1.2 GB of transcripts is a number worth knowing
  • First seen, last active, per agent
  • Notes explain exactly where each number comes from
Read-only by design

These folders hold your API tokens. The tool is built around that.

auth.json, oauth_creds.json, .credentials.json live next to the settings. agentconf treats that as the first design constraint, not an afterthought.

No write path exists

There are no write endpoints in the server and no write calls in the scanner. There is nothing to misclick and nothing to fat-finger.

Allowlist, not denylist

Only files the schema pack names are opened. Paths of kind credential are never read, not even to check their size.

Secrets masked before the UI

Values under headers, env, token, apiKey and friends are masked in the scanner. MCP env and header values are dropped entirely.

127.0.0.1 only

The server binds to loopback. No telemetry, no analytics, no update pings. Nothing leaves the machine.

Transcripts never read

Usage numbers come from counts, timestamps and the agents' own stats files. Prompt text and conversation content are not parsed.

7 MB, tens of milliseconds

One static Go binary. The first scan answers in about 30 ms; directory sizes and versions fill in behind it. Open it as often as you like.

Schema packs

The registry is the product. The binary is a viewer.

Each agent has one JSON pack: every key with its type, default, scope, summary, optional detail, flags and docs link. The UI renders whatever the pack describes. A tool with a hardcoded schema rots in months; a pack is a data file anyone can update, and the unknown-keys check tells you the moment it falls behind.

Install

Ten seconds. One binary. No runtime.

macOS and Linux, arm64 and amd64. Windows via go install. The web UI is embedded in the binary; there is nothing else to fetch.

$ curl -fsSL https://raw.githubusercontent.com/AviroopPaul/agentconf/main/install.sh | sh
$ agentconf
agentconf v0.1.0
  http://127.0.0.1:4242
  read-only. press ctrl+c to stop.
Installs to ~/.local/bin. Override with AGENTCONF_INSTALL_DIR. The script is 60 lines; read it first if you like.
$ go install github.com/AviroopPaul/agentconf/app/cmd/agentconf@latest
$ agentconf
Needs Go 1.27 or newer. The built UI is committed to the repo so the embed works from a clean clone.
$ brew install AviroopPaul/tap/agentconf
$ agentconf
Tap is published by the release pipeline after the first tagged release.
$ git clone https://github.com/AviroopPaul/agentconf && cd agentconf
$ make          # builds the frontend, then bin/agentconf
$ ./bin/agentconf
